Correction to the sweep

The exploration flagged .env and Admin_Credentials.pdf as "committed secrets." Both are false — verified against git ls-files: .env is properly gitignored (only .env.example is tracked) and the PDF is untracked. The real related risk is that secrets live in a OneDrive-synced .env (cloud-synced local exposure), not a git leak.

Opportunities EXTERNAL · POSITIVE›
  • First-mover in a paper-based market. Positioned as Rwanda's first digital sports ecosystem; most leagues still run on spreadsheets. Whole-lifecycle coverage (federation → pro league → school) is a real moat.
  • AKC3 youth pipeline. Digitizing school sport trains thousands of future athletes/managers on the platform young, and opens the youth-demographic sponsorship market.
  • Low-OpEx, consumption-based infra. Vercel / Supabase / Cloudinary / Pusher scale with usage and keep off-season costs down.
  • Three-stream revenue. Verification SaaS + match-day/banner ads + transfer fees — once real payments land.
  • Premium ad inventory. The live-reporting flow (match-day sponsorship) is high-engagement and directly monetizable.
  • Fast path to "operable." Finishing the CRUD gaps, wiring real payments, and adding indexes would move it from impressive demo to sellable product in a few sprints.
Threats EXTERNAL · NEGATIVE›
  • Vendor single-points-of-failure. Supabase (all data), Pusher (live scores — the sellable moment collapses if down), Cloudinary (crests + verification docs), Vercel (deploys). No documented DR / failover / multi-region — riskier given Rwandan connectivity variability.
  • Trust-dependent revenue. The B2B model hinges on accurate verification and standings; that logic has historically been fragile (score double-counting, winner-not-recorded, over-strict doc rules) — reportedly fixed, but it's the fragile surface.
  • Adoption risk. No documented federation partnerships or pilots; verification fees face price sensitivity; federations may resist cloud data sovereignty.
  • Key-person / small-team risk. Domain knowledge is concentrated; tight coupling (one deploy, one DB) amplifies it.
  • Stale issue register vs. reality. The tracked register lists admin/team/live-reporting as broken stubs, but recent work and the live run show these built and serving real data — treat the register as lagging and reconcile it.
  • Real-time cost exposure. Pusher is pay-per-message; a popular live match (goals/cards × thousands of concurrent fans) could spike costs unpredictably.

Bottom line

A genuinely impressive, feature-rich, running product (~7/10 production readiness) with a soft engineering-hygiene layer underneath. The vision and breadth are the standout strengths; the gaps are all in gates and finishing, not architecture.

  1. Make payments realIntegrate a live gateway + webhook/signature — unblocks the entire revenue model.
  2. Fix typecheck + add ESLint config + minimal CIGitHub Actions running typecheck and backend smoke tests. Cheap, high-leverage.
  3. Add DB indexes on hot foreign keysOne migration; protects against a scale cliff on fixtures/standings/events.
  4. Fill the CRUD gapsTransfers, team officials, registrations review, racing result entry.
  5. Add frontend e2e testsPlaywright for login → team registration → live reporting.
  6. Reconcile the issue register & move secrets off OneDriveSync the tracker to current reality; put .env secrets in a proper secret store.
